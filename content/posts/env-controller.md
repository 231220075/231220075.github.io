平时切换项目，经常要核对 Node、Python 和 Rust 的版本。拿 Node 来说，安装清单里即使有一个满足 `package.json` 要求的版本，当前终端也可能执行另一个。换到 Python，还要弄清虚拟环境基于哪个解释器。Rust 则多了一层，`rustc` 可能先经过 rustup，再根据当前目录和临时变量选择工具链。

这就是 Env Controller 的起因。我想在 macOS 上选一个工作区，看清它实际会用到哪些开发工具、版本是否满足要求，以及这个结果从哪里来。切换或卸载版本之前，我也想知道会改到哪里，哪些项目可能受影响。

## 从 mise 和 mise_gui 开始

[mise](https://mise.jdx.dev/) 已经能按项目管理多语言工具、环境变量和任务。[mise_gui](https://github.com/likaia/mise_gui) 则提供了图形化管理入口。我先在本机跑了上游原型，并通过它的管理服务验证安装、切换和卸载。环境诊断是改造的重点。在所评估的版本中，我用带空格的目录、本地覆盖配置和已激活的 venv 做了对照，发现仅靠扫描文件和读取配置，很容易把“找到了某版本”误报成“当前终端正在用它”。

项目沿用了 mise_gui 的 Flutter 桌面基础。从 [mise v2026.11.7](https://github.com/jdx/mise/tree/v2026.11.7) fork 出检查入口，直接复用 mise 的配置合并和工具解析，在选择发生的位置记录来源和覆盖过程。Python 和 Rust 则继续尊重各自管理器的规则。[pyenv](https://github.com/pyenv/pyenv) 和 [uv](https://docs.astral.sh/uv/concepts/python-versions/) 提供各自的 Python 安装记录，[rustup](https://rust-lang.github.io/rustup/overrides.html) 负责 Rust 工具链选择，[Homebrew](https://github.com/Homebrew/brew) 提供本机安装清单。

## 把工作区放在界面中心

第一版花了不少时间打磨扫描。它能处理隐藏目录和权限缺口，也保留了取消、恢复和复查的证据。试用时我才发现，打开应用后第一眼看到的是扫描范围、文件列表和结构化输出，实际需要的版本答案反而要自己找。后来我把主界面收成两个入口。「工作区环境」按工具展示当前版本、项目要求和来源，「本机工具库」按管理器列出可管理的安装。

核心也随之拆开。Rust 服务处理文件发现、项目约束、环境求值和命令核验，Flutter 只呈现这些结果。工作区检查可以启动新的交互式 zsh，也可以用 mise 求值后的环境运行探测。两种情况下都在指定目录核对实际工具身份。安装、项目版本声明和运行时选中的版本在数据模型里各有自己的位置，界面也分别呈现。

0.3 又补上已有终端。应用生成一条一次性命令，我在原 zsh 会话执行它。采集在子 shell 内完成，能继承别名、函数、命令缓存、临时导出变量和已激活的 venv，同时保留原会话状态。原始环境值通过本地通道交接，留在核心内存里。界面标出这是一次快照，之后改了环境就重新导入。

一次原生窗口验证里，项目要求 Node `>=24`，而测试会话中的别名实际调用了 22.14.0。界面同时显示版本、别名来源和「版本不符」。这比一排已安装版本更接近我想要的答案。

## 版本管理怎么落地

0.3 把 mise、pyenv、uv 和 rustup 接到了安装、项目选择和可恢复卸载。写入项目声明之后，界面提示重新核验实际版本，因为工作区仍可能受到终端变量或虚拟环境覆盖。Homebrew 在预览版里提供只读清单。

卸载分为预览、检查、备份和执行。程序先确认目标是管理器拥有的实体安装，检查选定范围里的项目声明、虚拟环境和符号链接，再核对当前用户可见的运行进程。发现引用时会中止。通过检查后才校验恢复副本并调用原管理器卸载，恢复入口保留在操作记录里。检查范围之外可能仍有引用，管理器自己的代理入口或缓存也可能需要复查。

这部分有几个问题是实测才暴露的。uv 可能先通过次版本别名报告解释器，简单取目录名会把别名当作实体安装。mise 删除最后一个版本后可能顺手删掉空的工具目录，恢复逻辑要在核对原父目录后重建它。最终我用四个真实管理器操作隔离 SDK 副本，完成卸载、恢复，再运行恢复出来的解释器或编译器。全新版本的联网下载安装、其他 Shell 和跨机器分发仍待验证。

## 这次最有用的收获

以前我会先问“还能多扫描哪些文件”。现在我会先问“这条证据能回答什么”。配置文件回答项目声明，管理器记录回答安装和选择，真正执行命令才能观察这次会话用到了哪个版本。这些结果往往都对，只是说的是不同层次的事。

还有一点是把失败和恢复放进设计的第一轮。分析结果保留未知项，写操作记录可复核的目标，卸载之前先想清楚怎样恢复。对我来说，项目做到 0.3 最有价值的变化，是把环境问题从反复试命令变成了一个能说清目录、会话、入口和证据的工作流。
